# E098 — Real H3 480p-class/3s SageAttention 2++ versus Sage3 operator speed

- **Experiment ID:** E098. **Mode:** exploration / deployment-operator comparison.
- **Problem addressed:** Determine the true steady-state cost of SageAttention 2++ and SageAttention3 on a real MiniMax-H3 attention call, including each API's online preprocessing, and identify major internal kernel costs where profiling is interpretable.
- **Hypothesis:** Sage3's FP4 attention kernel may be faster than Sage2++'s INT8/FP8 attention, but its Q/K/V centering, correction, and three operand packs may materially affect total latency.
- **Decision informed:** Which attention backend merits use or optimization for H3 at this actual 3-second video geometry.
- **Minimum valid setup:** Capture post-QK-RMSNorm/RoPE BF16 Q/K and BF16 V from a real prompt-1, first-step, block-25 H3 forward at **480×832, 73 frames (3.04 s at 24 FPS)**; this satisfies H3's `17n+5` frame contract. Verify its actual variable-length boundaries, 56 heads, and dimension 128. Compare BF16 SDPA, actual Sage2++ SM120 API, and official Sage3 Blackwell API on the valid main segment on idle GPU 0, then include the short padding segment and model-wrapper work separately. Use independent warmed CUDA-event latency measurement and an out-of-band CUDA profiler kernel breakdown. Check finite outputs and NMSE against BF16. Record API version/source/extension paths, input hashes, and raw batch times. The earlier 576×1024/124-frame cache is an explicit long-sequence diagnostic only, **not** the requested 3-second result.
- **Invalid cheap proxy to avoid:** random Q/K/V, SageAttention 1.0.6 misnamed Sage2++, reduced sequence length, attention-inner-kernel timing presented as full API time, profiling overhead included in benchmark latency, or preprocessed/quantized QKV passed as if their cost were free.
- **Expected outcomes:** Both native APIs run with stable timing and a profiler shows where time is spent; if Sage2++ cannot be built/loaded, report it as unavailable rather than substitute Sage1.
- **Decision for each outcome:** Prefer the faster sufficiently accurate actual H3 API; where preprocessing dominates, focus future optimization there. Do not extrapolate a single-block operator result to whole-DiT speed or video quality.
- **Stop condition:** One real main attention call plus necessary correctness smoke; no exhaustive layer/timestep sweep. Stop backend attempts after a documented source build failure or two plausible environment remedies.
- **Evidence class:** Necessary for selecting an H3 attention speed baseline; profiling is supporting evidence.
